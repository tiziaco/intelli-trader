# Phase 11.2 Plan 05: Venue-Account Provisioning Spine — Summary

One durable `venue_accounts` row now travels end to end without a restart — `provision`
writes it, `bring_online` turns it into a registered exchange under the exact
`(venue_name, account_id)` pair carrying that row's own `secret_ref`, and `account_for`
resolves it into a constructed account leaf — with `bring_online` having **exactly one
implementation** so boot is its bulk case rather than a second assembly path.

## What Was Built

**Task 1 — the tracer: row → runtime → leaf** (`5a93b4b1`)

- `VenueAccountStore.read_enabled_for(venue)` — venue-scoped, enabled-only, sharing
  `read_all`'s projection and its `venue_name` ASC / `account_id` ASC ordering contract.
  **No degrade policy here** (D-34 puts the whole policy in the manager).
- `VenueBundles.account_for(venue, account_id, **portfolio_args)` — D-21's mode-agnostic
  construction primitive over the shared memo.
- `itrader/venues/venue_account_manager.py::VenueAccountManager` — the live authority:
  - `read_enabled_for` wraps the store read in D-34's **narrow** probe
    (`inspect(engine).has_table("venue_accounts")`): missing table warns and returns `[]`;
    every other fault propagates.
  - `bring_online(row)` — the single implementation. Builds the `VenueSpec` with the
    **relocated `_read_account_secret_ref` logic**, delegates to `assemble_venue`,
    registers `exchanges[(venue_name, account_id)]` with the row's id verbatim, and records
    the runtime under the same pair.
  - `account_for` — asserts exists → enabled → online, then delegates.
- `VenueAccountNotProvisionedError` — carries the pair plus which of three causes applies.
- `tests/integration/test_account_provisioning_loop.py` — the end-to-end proof.

**Task 2 — create-only provisioning** (RED `51847745`, GREEN `977673cd`)

- `VenueAccountStore.create(...)` — a plain `INSERT`; the composite PK is the arbiter.
- `VenueAccountManager.provision(...)` — delegates the write and classifies
  `IntegrityError` on the error path into `DuplicateVenueAccountProvisionError`. No
  pre-check `SELECT`.
- The secret denylist is **asserted, not duplicated**: a structural test pins that
  `venue_account_store`'s guard *is* `venue_store`'s object (identity) and runs as the
  first statement of **both** writers (position).

**Final constructor signature** (the plan flagged this as unverified — no caller existed):

```python
VenueAccountManager(store, bundles, connectors, execution_handler, *, alert_sink)
```

## Deviations from Plan

### Auto-fixed blocking issues

**1. [Rule 3 — blocking] `upsert` structurally cannot express D-11; `VenueAccountStore.create` was added.**

The plan's Task 2 says to *"add `VenueAccountManager.provision(...)` delegating the write
to `VenueAccountStore.upsert`, and classify the database's `IntegrityError`"*. **`upsert`
never raises `IntegrityError`** — it is a `DELETE`-then-`INSERT` on the composite key
(`venue_account_store.py:139-159`), so a second write always succeeds. Implementing the
plan literally would have produced an `except IntegrityError` arm that can never fire,
behind a `provision` that **silently overwrites** the operator's `secret_ref`/`config` and
resets the engine-written `venue_uid` to `NULL` — disarming the D-04 trust-on-first-use
guard for that account. Every stated acceptance criterion would still have passed except
the behavioural one.

The existing code already documents the hazard from the other side:
`live_trading_system.py::_mint_account_rows` gates its `upsert` on a **pre-check
`SELECT`** precisely because *"an unconditional write would CLOBBER the operator's
`secret_ref` and `venue_uid` on every boot"* — i.e. the tree's only current create-ish path
uses exactly the TOCTOU shape D-11 rejects.

Fix: a create-only `VenueAccountStore.create` (plain `INSERT`, same reused denylist as its
first statement). The manager catches `IntegrityError` from it. This keeps SQL in the
store, keeps `grep -c '_assert_no_secret_keys'` on the manager at `0`, and makes the
duplicate refusal the database's decision rather than the application's.

**2. [Rule 3 — blocking] `DuplicateVenueAccountError`'s fields do not fit; a new type was added.**

The plan says to reuse it *"if its fields fit"*. It requires `first_portfolio` and
`second_portfolio` (`portfolio.py:204-222`) — it reports two **portfolios** colliding on
one account. A provision refusal has no portfolios in it; the collision is between an
existing row and a new write. Reusing it would mean inventing two portfolio names that do
not exist. `DuplicateVenueAccountProvisionError` was added beside it, with the distinction
documented in both docstrings.

### Design decisions taken where the plan deferred to the executor

**8. The constructor drops the planner's proposed `venue_name`.** All three public methods
(`read_enabled_for`, `bring_online`, `account_for`) already take the venue explicitly — the
row carries it in `bring_online`'s case — so a constructor copy would be a second source of
the same fact, the shape this milestone is removing elsewhere. `alert_sink` is **required**
(not `Optional`, despite `assemble_venue` accepting `None`): an account brought online with
nowhere to escalate a venue-identity mismatch is a silently-disarmed guard.

**9. `VenueBundles.account_for` forwards `account_id` to the factory and gained `spec=`.**
The plan's `account_for(venue, account_id, **portfolio_args)` collides with itself:
`account_factory` also takes `account_id=`, so passing it in `portfolio_args` raises
`TypeError: got multiple values`. Resolved by forwarding the pair's `account_id` into the
factory — which is D-21's semantics exactly (the pair *is* the identity) — and documenting
that callers must not repeat it. A keyword-only `spec=None` was added for the memo-**miss**
case; the expected case is a memo hit, where it is unread.

**10. `bring_online` registers the exchange unconditionally.** The legacy boot loop skips
registration when `bundle.connector is None` (`live_trading_system.py:2191`), which means a
**named paper account is never registered and every order for it fails closed on a lookup
miss**. The new single path registers regardless. The legacy path is untouched (D-39 scope),
so this is additive, not a behaviour change to the existing boot.

**11. The `secret_ref` relocation preserves the semantics that matter, and the source is not deleted.**
`_read_account_secret_ref` degrades clean on a **store read failure** and normalizes with
`account_id or DEFAULT_ACCOUNT_ID`. The relocation reads `secret_ref` off the row it was
**already handed**, so there is no second store read to fail and no id to coerce; a NULL
pointer still means "no per-account credentials" (the D-06 paper shape), and a well-formed
pointer is still carried to the resolver untouched. Per D-39 this plan is purely additive:
the original function still stands in `live_trading_system.py` and is deleted by a later plan.
