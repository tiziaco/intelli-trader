# Phase 11.2 Plan 08: PortfolioFactory + one storage site for the account pair — Summary

D-23 gives the `(venue_name, account_id)` pair exactly one storage site — the
account leaf — and exposes it through read-only `Portfolio` properties, so a
portfolio's idea of its account can never drift from the leaf's own identity. D-24
introduces a composition-owned `PortfolioFactory` that maps a portfolio definition
to its runtime graph through the mode-agnostic `VenueBundles.account_for` primitive
(D-21), constructed with real dependencies and no `Optional` collaborator. The live
authority wiring (`VenueAccountManager.account_for` + the create/materialize split)
and the factory's adoption on the production `add_portfolio` path are deferred to
plan 09 per the owner decision.

## What shipped

### Task 1 — D-23: one storage site for `(venue_name, account_id)` (commit `bd5c223c`)
- `Account` ABC declares `account_id` / `venue_name` (class-level, default `None`) so
  **any** `Account` — including a test double — is safe to read under the property
  seam without `AttributeError`.
- `SimulatedCashAccount` / `SimulatedMarginAccount` accept and store the pair
  (optional keywords); `VenueAccount` gains `venue_name` alongside its required
  `account_id`.
- `Portfolio.venue_name` / `.account_id` are now **read-only `@property`** over
  `self.account`. The `self.account_id =` / `self.venue_name =` storage is removed;
  the constructor params survive only for call-site compatibility and to seed the
  legacy `exchange` derivation (D-07).
- The pair is threaded onto the compute leaf: `add_portfolio` → `_new_compute_account`
  → the paper `account_factory` closure → `new_account` → `VenueAccountConfig` → the
  leaf. The leaf carries the **portfolio's own** pair (not the compute venue's), so
  backtest is byte-identical (`'paper'` / `None`) and a live portfolio's leaf carries
  its real `('okx', 'acct-…')` pair — which is what `_persist_definition` writes.
- Tests: new D-23 property tests (reads from the leaf, read-only → `AttributeError`,
  no second storage site in `__dict__`) + rewritten seam pins.

### Task 2 — D-24: `PortfolioFactory` over `VenueBundles.account_for` (commit `07fa69c9`)
- New `itrader/portfolio_handler/portfolio_factory.py`. Constructed with real deps
  (`venue_bundles`, `environment`/`sql_engine`, `compute_venue`) — **no `Optional`
  collaborator, no `None`-then-assign, no post-construction setter**, so the
  `if self._venue_bundles is None: raise` shape that existed only because that
  collaborator was `Optional` has **no counterpart** here.
- `materialize(...)` resolves the account through the mode-agnostic D-21 primitive
  `VenueBundles.account_for`, builds the id-scoped `state_storage` explicitly, enters
  the Decimal domain via `to_money`, and constructs the `Portfolio` over the leaf.
- Direct tests (`tests/unit/portfolio/test_portfolio_factory.py`) with an **identity
  sentinel** (the exact object `account_for` returned), because the oracle drives the
  LEGACY construction arm and a factory-only edit would go false-green: attaches the
  `account_for` account, forwards the pair, normalizes an absent id to
  `DEFAULT_ACCOUNT_ID`, passes a real `state_storage`, cash is `Decimal`, an
  `account_for` refusal PROPAGATES (no fallback leaf), and `venue_bundles` is a
  required construction dependency.

### Task 3 — factory wiring: DEFERRED to plan 09 (see Deviations)

## Deviations from Plan

### Owner-directed scope reshape (recorded, per owner sign-off)

**1. [Owner decision] Live `account_for` wiring + factory integration DEFERRED to plan 09.**
- Plan 07 made it structurally impossible to inject a `PortfolioFactory(VenueAccountManager)`
  into `compose_engine` — `compose_engine` builds `PortfolioHandler` internally, but
  `VenueAccountManager` is built *after* `compose_engine` returns (it needs
  `engine.execution_handler`). Any wiring holding a VAM reference before VAM exists is
  the `None`-then-assign / late-init pattern this project forbids.
- Per owner sign-off, plan 08 does the **mode-agnostic structural half** only:
  `PortfolioFactory` is built with `VenueBundles` (never VAM), and `materialize` uses
  `VenueBundles.account_for` (D-21), not `VenueAccountManager.account_for` (D-21's live
  authority, which stays plan 09). No `Optional[VenueAccountManager]` placeholder was
  introduced anywhere.

**2. [Owner decision] `PortfolioHandler._new_compute_account` / `self._venue_bundles` KEPT (plan Task 2 said DELETE them).**
- Post-07, `compose_engine` is called before `VenueAccountManager` is built, and the
  in-memory live arm (`system_db_backend is None`) builds NO VAM at all. Deleting
  `_new_compute_account` / `_venue_bundles` and replacing them with a VAM-based path
  would strand the live in-memory arm (no account-build path, nothing replacing it).
  Per owner sign-off, both are LEFT WORKING; plan 09 deletes them when it wires
  `account_for` at materialize (with a real VAM online, no late-init). The plan's Task 2
  acceptance criteria `grep -c '_venue_bundles' == 0` and `grep -c '_new_compute_account' == 0`
  are therefore **superseded by the owner decision** and intentionally NOT met.

**3. [Owner decision + technical blocker] Task 3 production wiring (compose_engine / composition roots) DEFERRED to plan 09.**
- Routing the production `add_portfolio` path through `VenueBundles.account_for` is
  **incompatible this wave** with the backtest `account_id is None` invariant
  (`compose.py:160-163`, `test_legacy_add_portfolio_shape`, `test_account_for_returns_none_when_no_account_named`):
  `account_for(venue, account_id)` forwards its single `account_id` to BOTH the memo
  key and the leaf, so an unnamed backtest portfolio's leaf would become
  `DEFAULT_ACCOUNT_ID` (`'default'`) instead of `None`. Collapsing the memo-key /
  leaf-identity split onto `account_for` requires the create/materialize + real-account
  unification that is explicitly plan 09's work.
- Injecting the factory into `PortfolioHandler` as a stored-but-unused **required**
  collaborator (while keeping `_venue_bundles` per deviation 2) would make the handler
  hold MORE overlapping account-build collaborators — the opposite of D-24's shrink —
  and churn ~9 `compose_engine` / `PortfolioHandler` call sites for zero production
  behavior change. An `Optional` factory param is the exact anti-pattern the plan
  forbids. So the factory is delivered as a fully-tested standalone D-24 seam; plan 09
  consumes it. Task-3 grep criteria (`portfolio_factory` in `compose.py`,
  `PortfolioFactory` in `backtest_trading_system.py`) are **superseded** by this deferral.
- `grep -c 'VenueAccountManager' backtest_trading_system.py` == **0** holds (the backtest
  arm never referenced VAM), so that criterion is satisfied trivially.

### Code-wins corrections (from the pre-dispatch audit — the code won every time)

**4. [Discrepancy 1 — the plan's central premise was FALSE] The `Account` ABC declared NEITHER `account_id` NOR `venue_name`.**
- The plan (D-23 truth + Task 1 "read first") claimed "the `Account` ABC already
  declares `account_id`" and the leaf "carries `venue_name` alongside the `account_id`
  it already carries." Reality (HEAD `11f6bef0`): `account/base.py` declared only
  `is_venue_truth`; the `Simulated*` leaves stored **neither** `account_id` nor
  `venue_name`; only `VenueAccount` stored `account_id` (and it lacked `venue_name`).
- A `portfolio.account_id` property reading `self.account.account_id` would have
  `AttributeError`'d on **every** backtest/paper portfolio (all-spot
  `SimulatedCashAccount`) and broken the oracle. Fixed by adding **both** fields to the
  ABC (default `None`) and to the two `Simulated*` leaves, plus `venue_name` to
  `VenueAccount` — exactly as the audit flagged.

**5. [Discrepancy 2 — under-scoped files] `paper_plugin.py`, `bundle.py`, `okx_plugin.py` were NOT in `files_modified` but had to change.**
- Threading the pair onto the compute leaf required `VenueAccountConfig.venue_name`
  (`bundle.py`), the paper `new_account` passing the pair to the leaf + the paper
  `account_factory` closure gaining `venue_name` (`paper_plugin.py`), and the same for
  the OKX arm to keep the shared `account_factory` contract consistent and give
  `VenueAccount` a real `venue_name` (`okx_plugin.py`). All added.

**6. [WR-08 contract] `venue_name` exempted from the paper `account_factory` no-default rule.**
- `venue_name` was made a **defaulted** (`= None`) keyword on both `account_factory`
  closures. The WR-08 no-default rule guards the four fail-loud knobs (cash / margin /
  account_id / persistence seam) whose absence is a silent substitution; `venue_name`
  is pure identity where `None` is the honest "names no venue" (the backtest case), not
  a fabricated value. `test_paper_account_factory_has_no_defaulted_parameter` was updated
  to exempt `venue_name`, and the `VenueAccountManager.account_for` → `bundles.account_for`
  → paper-closure path (test `test_provision_then_bring_online...`) stays green because a
  defaulted `venue_name` does not require every caller to pass it.

**7. [Stale acceptance criteria] Suite floor `2879` raised to the real `2958`; `_new_compute_account` grep-to-0 and `VenueBundles`-delete criteria dropped per deviations 2–3.**

## D-23 implementation note (brief vs plan truth)

The code-wins brief *preferred* storing the pair on `Portfolio` itself over
"reaching through `self.account`". I implemented the **canonical D-23** (read-only
properties over `self.account`, leaves carry the pair) because that is what the plan's
`must_haves.truths` (D-23: "read-only PROPERTIES over `self.account`") and the Task 1
acceptance criteria (`grep -c 'self.venue_name =' == 0`, `def venue_name` `@property`,
`portfolio.venue_name is portfolio.account.venue_name`) require, and it is the only
form that makes drift *structurally impossible* rather than merely guarded. The
brief's `AttributeError` concern is fully addressed by threading identity onto every
leaf construction (compute leaf via `_new_compute_account`; direct-construction tests
via `compute_account`) and by the ABC's `None` class defaults.
