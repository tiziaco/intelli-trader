# Phase 11.2 Plan 06: Account-Level Venue Config Precedence + D-04 Guard Observability Summary

Wired `venue_accounts.config_json` into `VenueAccountManager.bring_online` as a raising three-key
allowlist (`sandbox`/`region`/`market_type`), gave those keys a real destination on `VenueSpec` and
threaded them to the OKX connector + bundle builders, cleared the `market_type='spot'` hardcode that
would have made one key inert, and made the D-04 UID guard report outcome-plus-reason per
`(venue, account_id)`.

## What was built

**Task 1 — the account-level knobs reach a real consumer (D-38 blocker cleared).**
- `VenueSpec` (`trading_system/venue_spec.py`, a TABS file, outside `files_modified`) gained
  `sandbox: Optional[bool]`, `region: Optional[str]`, `market_type: Optional[Literal["spot","derivative"]]`,
  all defaulting to `None` ("no override"); `build_venue_spec` threads them so the SEAM-03 identity
  invariant (a spec re-built from its own fields compares equal) still holds.
- `okx_plugin.build_bundle` now reads `market_type` from the spec, defaulting to a named module-level
  `_OKX_DEFAULT_MARKET_TYPE = "spot"` — the OKX **venue-level** default, deliberately NOT falling
  through to `VenueAccountConfig`'s `"derivative"` default (which would invert
  `_cash_stream_nets_holds` for every OKX account). The parameterized sibling site
  (`market_type=config.market_type` in `new_account`) is untouched; the `market_type=` kwarg count is
  unchanged at **2** (before: 2, after: 2), and `market_type="spot"` is now **0** (before: 1).
- `OkxConnectorPlugin.build` applies the account's own `sandbox`/`region` as pydantic-settings init
  kwargs (highest-priority source) on **both** the ambient and the resolved-credential paths; a
  helper `_connection_overrides` drops `None`s so absence is never forwarded as an override. Two now-unused
  `# type: ignore` comments were removed (the `**dict` splat satisfies mypy).

**Task 2 — the raising allowlist merge (T-11.2-06-01 mitigation).**
- `VenueAccountManager._merge_account_config` validates the incoming `config_json` against
  `_MERGEABLE_CONFIG_KEYS = frozenset({"sandbox","region","market_type"})` and raises the new typed
  `UnknownVenueAccountConfigKeyError` (registered in `core/exceptions/__init__.py`, docstring list +
  `__all__`) on any other key, **before** any assembly — so a refused config brings nothing online.
- The merge uses the shared `outils/dict_merge.py::recursive_merge` (no hand-rolled merge); precedence
  is account-over-venue, one direction. `config_json = {}` and `= None` are indistinguishable — both
  leave every venue default in force, neither raises.

**Task 3 — the D-04 guard reports outcome AND reason (D-40).**
- `assert_venue_uid` returns a frozen `VenueUidGuardOutcome(armed, outcome, reason)` instead of a bare
  side effect. The **six** inertness paths enumerated from the guard's own code each get a distinct
  reason constant: `REASON_FETCH_RAISED`, `REASON_UID_UNAVAILABLE_CREDENTIALED`,
  `REASON_NO_VENUE_IDENTITY`, `REASON_STORE_READ_FAILED`, `REASON_NO_ACCOUNT_ROW`,
  `REASON_RECORD_WRITE_FAILED`. Armed sub-states carry their own reasons too.
- `VenueLifecycle` captures the outcome at `start()` (the connect seam) and adds three
  **lifecycle-level** reasons for states where the guard never runs (`GUARD_REASON_NOT_STARTED`,
  `GUARD_REASON_PAPER_NO_CONNECTOR`, `GUARD_REASON_COLLABORATORS_ABSENT`), exposed via
  `venue_uid_guard_outcome`.
- `VenueAccountManager.venue_uid_guard_active()` surfaces the per-`(venue, account_id)` outcome map,
  read live through each online record's lifecycle.

## The six inertness paths (which set was enumerated)

Per the audit brief's discrepancy 10, the "six" are the guard's OWN paths, counting the **silent
credential-less return** as one and **excluding** the lifecycle collaborator-absent skip:

1. `_fetch_uid` — plugin's `fetch_venue_uid` raised → `REASON_FETCH_RAISED`
2. `_fetch_uid` — credentialed venue yielded no uid → `REASON_UID_UNAVAILABLE_CREDENTIALED`
3. `_fetch_uid` — credential-less venue, no identity (paper) → `REASON_NO_VENUE_IDENTITY`
4. `store.get` raised → `REASON_STORE_READ_FAILED`
5. no account row → `REASON_NO_ACCOUNT_ROW`
6. first-connect record write failed → `REASON_RECORD_WRITE_FAILED`

The lifecycle-level skips (no connector; collaborators absent) are surfaced too, but as
`lifecycle.py` reasons, kept separate so an operator can tell "the guard ran and degraded" from "the
guard was never reached".

## Deviations from Plan

### Owner-authorised extensions (outside `files_modified`)

**1. [Owner decision] Extended `VenueSpec` so the allowlisted keys reach a real consumer.**
- **Issue:** the plan asserted `config_json = {"sandbox": True}` produces a `VenueSpec` with
  `sandbox=True`, but `VenueSpec` had exactly four fields (`execution_venue`, `data_provider`,
  `account_id`, `secret_ref`) — no `sandbox`/`region`/`market_type`. Shipping the allowlist over no
  destination is forbidden by the plan's own threat T-11.2-06-02.
- **Fix:** added the three fields to `venue_spec.py` (TABS) and threaded them through
  `build_venue_spec` → `OkxConnectorPlugin.build` / `build_bundle`.
- **Files:** `itrader/trading_system/venue_spec.py`, `itrader/venues/okx_plugin.py`.
- **Commit:** f9c1eff1.

**2. [Owner decision — Rule 2] Per-`(venue, account_id)` connector memoization guard.**
- **Issue:** `ConnectorProvider.get` reads the spec only on a memo MISS. With D-38 letting an account's
  `config_json` carry `sandbox`/`region`, a second account on the same pair with different routing
  would silently reuse the first connector's session.
- **Fix:** `get` now records the session identity (`secret_ref`/`sandbox`/`region`) per pair and raises
  `ValidationError` if a later same-pair call disagrees; different `account_id`s remain independent.
  Pinned by three new tests in `tests/unit/connectors/test_provider.py`.
- **Commit:** f9c1eff1.

### Code-wins corrections (plan text vs current tree)

**3. [Rule 1 — code-wins] Guard arming is NOT moved into `bring_online`.**
- **Plan claim:** "arm the guard inside `bring_online`". **Reality:** `bring_online` never connects;
  the guard arms post-connect inside `VenueLifecycle.start()`. Moving arming into `bring_online` would
  require an unstated connect-at-bring-up behavioural change (audit discrepancy 9).
- **Decision (recorded, not slid into):** the guard keeps arming at connect. The manager **surfaces**
  the per-pair outcome, reading it live from the lifecycle that owns it — which satisfies D-40's
  "outcome+reason per pair on the status surface" without changing when the connect happens. Before
  `start()`, a pair reports `GUARD_REASON_NOT_STARTED` (never a stale armed value).
- **Commit:** dd9ff4d5.

**4. [Rule 2] Value-validation added beyond the plan's key-only allowlist.**
- The plan specified refusing unknown KEYS. Two allowlisted keys fail SILENTLY on a bad VALUE:
  `market_type="spott"` sails through as a derivative and flips `_cash_stream_nets_holds` (cash
  accounting), and a JSON string `sandbox="false"` is truthy and inverts the host. Added
  `_assert_config_values` raising `ValidationError` for both. `region` is deliberately left to
  `OkxSettings.region`'s own `Literal` (fail-loud at build) so the venue keeps its vocabulary — no
  copy to drift.
- **Commit:** ae3f119c.
