## Why the original 11.2-09 was pulled

The keystone plan asserted `materialize -> VenueAccountManager.account_for` with an ACCT-03
raise in its must_haves and Task-3 tests, but **no task wired VAM into the `PortfolioFactory`**,
and the wiring it implied is structurally impossible without a forbidden late-init /
`Optional`-collaborator pattern. Root cause: a four-node construction cycle on the LIVE arm.

```
portfolio_handler ─needs→ factory ─needs→ VAM ─needs→ execution_handler ─needs→ portfolio_handler
```

Every edge is a **use-time** dependency, not a construction-time one — the cycle is an
artifact of eager construction-time injection.

## The decision (D-43) — extract the exchange registry

**The one FALSE edge is `VAM → execution_handler`.** VAM touches the execution handler in
exactly ONE place:

```python
# itrader/venues/venue_account_manager.py:448 — the ONLY use of self._execution_handler
self._execution_handler.exchanges[(venue_name, account_id)] = bundle.exchange
```

It never calls a method and never reads — it reaches into `execution_handler.exchanges`
(a plain `dict[tuple[str, str], Optional[AbstractExchange]]`, declared at
`execution_handler.py:143`) to register one built exchange. That is a Law-of-Demeter
reach-in, independent of the cycle.

**Cut it by extracting the exchange registry into a composition-root-owned component that
BOTH `ExecutionHandler` and `VenueAccountManager` receive.** VAM depends on the registry,
not the handler. This single cut dissolves the cycle.

**Do NOT cut `execution_handler → portfolio_read_model`.** It is a legitimate use-time read
(MPORT-07 / D-27 account isolation): `execution_handler.py:252-254` calls
`self._portfolio_read_model.account_for(event.portfolio_id)` per order. It is already a
narrow `PortfolioReadModel` Protocol and already `Optional`. Once the VAM→handler reach-in
is gone, this edge is not part of any cycle — leave it exactly as-is.

## Target construction order (no late-init anywhere)

```
1. exchange_registry            root owns — the shared (venue,account_id)->exchange map
2. VAM(store, bundles, connectors, registry=exchange_registry, feed_binder, alert_sink)   ← no execution_handler
3. factory(venue_bundles, authority=VAM)                                                   ← REAL VAM at construction
4. compose_engine(ctx, venue_bundles, exchange_registry, portfolio_factory=factory)
      -> portfolio_handler(factory)          builds leaves THROUGH the factory
      -> execution_handler(exchange_registry, read_model=portfolio_handler)   ← MPORT-07 intact
5. VAM.bring_online  writes into exchange_registry;  execution_handler reads it
```

The factory holds a **real** VAM at construction; VAM's `_online` map fills between
construction and the first `materialize` at rehydrate time — ordinary object lifecycle,
NOT deferred wiring. `materialize` is only CALLED during rehydrate (which plan 07 already
moved ABOVE the venue-wiring so accounts are online first) and at the runtime add path,
both after `bring_online`.

## What this buys over the rejected alternatives

- **vs option 2 (composition-root-owned factory / PortfolioHandler loses account-building):**
  no `add_portfolio` API upheaval, no ~130-call-site retarget. The factory injects straight
  into `compose_engine`; PortfolioHandler keeps building leaves through it.
- **vs option 3 (reorder boot / build exec-handler before compose):** no rework of the
  MPORT-07 read-model edge, no forbidden late-init, no dissolution of the shared compose seam.
- **Oracle seam barely touched:** `compose_engine` gains an `exchange_registry` param and a
  `portfolio_factory` param and stops letting `ExecutionHandler` privately own the registry.
