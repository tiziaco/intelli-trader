# Phase 11.2 Plan 09: D-43 Exchange-Registry Extraction + Create/Materialize Split Summary

Cut the four-node LIVE construction cycle by extracting the `(venue,account_id)->exchange` registry
(D-43), gave `PortfolioFactory` a real mode-agnostic authority built before `compose_engine`, split
`add_portfolio`'s durable write from its runtime build (D-25), deleted the two guards that only
existed to make rehydrate's re-entry safe, closed ACCT-07 structurally, and corrected the flagship
multi-portfolio fixture (WR-11). **ACCT-03 is delivered as the RAISE** — the venue-truth leaf at
construction is deferred to COMP-07/Phase 12 per the owner's wave-5 decision.

## Accomplishments

- **Task 1 — D-43 exchange-registry extraction (`194ac62f`).** `ExecutionHandler` receives a
  composition-root-owned `exchange_registry` (was `venue_bundles`); `init_exchanges` + the paper
  seed/connect moved to the module-level `seed_exchange_registry` helper, run by `compose_engine`.
  `VenueAccountManager` receives the shared registry (was `execution_handler`) and `bring_online`
  writes its own injected map — the one false edge whose extraction dissolves the LIVE cycle. The
  MPORT-07 `execution_handler -> portfolio_read_model` edge is left exactly as-is. The live root
  creates the shared registry before compose and hands the SAME object to both handlers.
- **Task 2 — PortfolioFactory real authority (`7f5c4a90`).** `PortfolioFactory` holds one REQUIRED
  `authority`; `materialize` is branch-free (no `if backtest`). Backtest authority =
  `ComputeAccountAuthority` (account_id None, never raises). Live authority =
  `VenueValidatedComputeAuthority`: it asks the real `VenueAccountManager.assert_available` to
  validate the pair (the ACCT-03 raise) then builds a COMPUTE leaf carrying the real pair. The
  handler builds every leaf through the injected factory (no `_new_compute_account`, no held
  `VenueBundles`). The manager is built ABOVE compose (the D-43 cut made it cycle-free), no
  late-init, no `Optional`.
- **Task 3 — create/materialize split + ACCT-07 (`e67d83ad`).** `add_portfolio` = `create` (durable
  write) then `materialize` (runtime build + register), plain-data signature byte-unchanged.
  `rehydrate_portfolios` materializes ONLY (public `materialize` + new public `has_portfolio`
  predicate; no `add_portfolio`, no `create`, no `_portfolios` reach-in). The null-account early
  return and the GATED-ON-ABSENCE gate are DELETED; ACCT-07 closes structurally.
- **Task 4 — WR-11 + factory ACCT-03 pins (`86f8e072`).** `_PaperPair` names two distinct paper
  accounts + real `venue_name` and registers a per-account exchange for each pair (mirroring
  `bring_online`), so the two portfolios resolve to two DIFFERENT exchange objects. Factory-level
  ACCT-03 pins assert the missing (NOT_PROVISIONED) and disabled (DISABLED) causes are
  distinguishable.

## Owner scope clarification — ACCT-03 delivered as the RAISE (READ THIS)

The plan's original must_have asserted `materialize` yields an `is_venue_truth is True` venue-truth
leaf on the live arm. During execution I found this is **infeasible without COMP-07**: a real
`VenueAccount` leaf's `.balance` raises `StateError` until its first venue snapshot (T-05-07,
`account/venue.py`), while `Portfolio.__init__` reads `total_equity`->`account.balance`
unconditionally at construction (`metrics_manager.py:88`, `portfolio.py:299/307`). So a venue-truth
leaf cannot be the construction-time leaf, and the venue-truth swap infra (`_attach_venue_accounts`)
was already **owner-deferred to Phase 12 / COMP-07 (sign-off 2026-07-22)**. I surfaced this as a
Rule-4 blocker; the owner decided **Option 1 (wave 5, 2026-07-24)**: deliver ACCT-03 as the RAISE
(REQUIREMENTS.md: "a live portfolio naming no venue account RAISES at composition time"), keep the
compute leaf at construction, defer the venue-truth leaf to COMP-07/Phase 12. This is a **deliberate
scope clarification, not a gap** — the security guarantee (never trade against a fabricated balance)
is delivered; the venue-truth leaf lands when the snapshot lifecycle does. `VenueAccountManager.account_for`
stays as the venue-truth resolution primitive COMP-07 will wire.

## Deviations from Plan

**1. [Owner decision] Venue-truth leaf deferred; ACCT-03 = the RAISE (Option 1).** See the section
above. The live authority builds a compute leaf carrying the real pair, gated by the raise.

**2. [Rule 1 - correctness] `assert_available` scoped to EXISTS + ENABLED, not "+ brought-online".**
The wave-5 rework note said "exists + enabled + brought-online". I scoped `assert_available` (the
compute-leaf gate) to exists+enabled and kept the `online` check on `VenueAccountManager.account_for`
(the COMP-07 venue-truth seam). Rationale: a compute leaf needs no assembled venue session, and
requiring "online" crashed a single-venue live boot on a validly-provisioned FOREIGN-venue portfolio
(a `binance` portfolio in an `okx` boot, whose venue this process never assembles) — which
REQUIREMENTS.md does not ask for ("naming NO venue account", not "on the assembled venue"). This is
what made `test_distinct_account_invariant`'s two multi-venue cases green without rewriting their
MPORT-02/CR-01 intent.

**3. [Rule 3 - blocking] `seed_exchange_registry` placed in `execution_handler.py` (module-level),
called by `compose_engine`.** The plan said "MOVE into compose_engine". I put it as a shared
execution-domain helper so the ~5 direct-construction test sites reuse the exact production recipe
(`tests/support/venue_wiring.py::backtest_exchange_registry`) rather than drift five copies — the
existing venue_wiring philosophy. The logic still runs at compose time.

**4. [Rule 1 - correctness] Null-account write fails loud via the composite FK (IntegrityError),
not a typed raise.** The plan permitted either a typed raise or a plain deletion. I deleted the
null-account early return; on the live arm a null-account portfolio now hits the composite FK / NOT
NULL (IntegrityError) at `create`, which the plan names as "the account check on the write side".
`test_a_portfolio_naming_no_account_writes_no_row` was rewritten to
`test_a_live_portfolio_naming_no_account_fails_loud_on_the_write`.

**5. [Rule 3 - blocking] Collateral test fixes beyond the plan's enumerated files (all ACCT-03
collateral).** ACCT-03's raise broke pre-existing tests that created live portfolios without a
provisioned account: `test_strategy_external_add_lifecycle` (4 tests) now provisions a per-portfolio
paper venue account and names it; `test_multi_account_composition` reaches the VenueBundles memo
through the factory authority (the `_venue_bundles` reach-in moved off both handlers). These are
"fix the tests to the corrected contract" per the coordinator.

**6. [WR-11 realization] Offline `_PaperPair` is the in-memory arm (no SQL FK).** `build_paper_replay_system`
has no Postgres spine, so the offline fixture has no definition-write FK and no `VenueAccountManager`.
It therefore registers the two per-account exchanges BY HAND (via the shared `VenueBundles` memo,
which post-D-43 builds a distinct `SimulatedExchange` per pair) — the same registration `bring_online`
performs on the SQL arm. The SQL-spine restart fixture (already correct) exercises the real FK +
venue_accounts seeding.
