# Phase 11.2 Plan 11: Durable Portfolio Pause/Retire + D-33 Account-Disable Refusal Summary

**Portfolio pause (`enabled`) and retire (`is_deleted`) are now DURABLE and survive a restart; `delete_portfolio`'s "never touches the definition store" gap is closed; and a venue account refuses to be disabled while a live portfolio depends on it — resolved against the durable store, not a live-portfolio collaborator.**

## Performance

- **Duration:** ~45 min
- **Completed:** 2026-07-24
- **Tasks:** 3
- **Files modified:** 9 (+1 test file created)

## Accomplishments

- **Task 1 — targeted flag writers on `PortfolioDefinitionStore` (`f6ca0680`).** `set_enabled` / `set_deleted` are targeted UPDATEs (never the DELETE-then-INSERT `upsert` that would clobber `config_json`), documenting D-32's pause-vs-retire distinction; `update` added to the sqlalchemy import. Also added `live_portfolio_ids_for_account` — the D-33 durable read (`enabled=True AND NOT is_deleted`). The `enabled=True` hardcode in the create path is no longer the only writer of the column (ACCT-10/WR-04).
- **Task 2 — durable pause/resume/retire + is_deleted-aware boot (`4c4356a0`).** `deactivate_portfolio` / `activate_portfolio` perform the persist and the in-memory flip as one handler operation, crash-safety-ordered (deactivate persists BEFORE flipping, activate flips BEFORE persisting) so the surviving state after any crash is always "stopped". `delete_portfolio` now persists `is_deleted=True` — the real WR-04 defect (it flipped ARCHIVED and dropped the registry entry but never touched the store). Full round-trip integration test on the SQL spine (create → deactivate → restart INACTIVE → activate → restart ACTIVE → delete → restart gone → successor claims the released pair).
- **Task 3 — D-33 account-disable refusal (`d098c5f5`).** `VenueAccountManager.set_enabled` refuses a disable while any LIVE portfolio references the account, naming the account, the blocking portfolio ids and the remediation; a paused/retired portfolio releases the block; enabling is never refused. Backed by `VenueAccountStore.set_enabled` (targeted UPDATE) and the new `VenueAccountInUseError`.

## Decisions Made

See `key-decisions` frontmatter. The load-bearing one: **the D-33 refusal is resolved against the durable store, not a live in-memory portfolio collaborator** (per the coordinator's scope steer). `VenueAccountManager` builds a read-only `PortfolioDefinitionStore` over the `SqlEngine` its `VenueAccountStore` already owns (`store.backend`), so the constructor signature is unchanged — no new injected collaborator, no `compose.py` / `live_trading_system.py` edits, no undeclared shared file with plan 10, and the one-directional layering (facade → manager → storage) is preserved. A pause/retire is durable, so the block a disable must respect is durable too.
