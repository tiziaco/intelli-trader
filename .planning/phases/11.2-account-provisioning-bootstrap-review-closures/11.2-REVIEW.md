# Phase 11.2: Code Review Report

**Reviewed:** 2026-07-27
**Depth:** standard
**Files Reviewed:** 76
**Status:** issues_found

## Summary

Phase 11.2 builds a genuinely well-factored venue-account domain: `VenueAccountManager`,
`FeedConnectionBinder`, `PortfolioDefinitionStore`, the D-32 two-flag lifecycle and the
`p112` partial-index migration are individually correct and individually well-tested (184
tests in the phase's own unit/integration scope pass; I verified the migration chain
end-to-end on SQLite and confirmed the `create_all` and `upgrade head` schemas agree on the
partial index, including the `sqlite_where` predicate actually reaching the DDL).

The defects are all at the **wiring seam between those new collaborators and the running
live system** — precisely the place the phase's own test strategy does not reach, because
every new unit and integration test constructs the collaborators directly rather than
through `build_live_system`.

Four of them are blocking:

* the `VenueAccountManager` is built as a **local variable** and never attached to the
  facade, so the phase's headline deliverable — runtime account provisioning without a
  restart (ACCT-02 / D-26 / D-27) — has **no reachable entry point at all**, and the
  typed refusal message tells operators to call an attribute that does not exist;
* the `FeedConnectionBinder` re-borrow path builds a provider that is never subscribed,
  never halt-wired and never stream-state-wired, and abandons the previous provider
  without stopping it — so a re-borrow silently blinds the live feed and disarms the data
  arm's halt path;
* the `venue_accounts` map feeding `StreamRecoveryHandler` is declared and never
  populated, so reconnect-resume no longer takes the fresh REST snapshot its own contract
  ("never resume blind") requires;
* `bring_online` publishes an account's exchange into the order-routing registry before
  anything connects the session or wires its halt signals, and nothing registers the
  lifecycle with the facade.

Everything else is a WARNING: durable rows written before their validating guard runs,
success logs on silent no-op writes, a parity gate that does not cover the one schema
change the phase makes, a multi-account teardown that closes every connector, and several
security-guarantee docstrings that overstate what the ACCT-03 check actually does.

## Critical Issues

### CR-01: `VenueAccountManager` is never attached to the live system — runtime provisioning is unreachable

**File:** `itrader/trading_system/live_trading_system.py:1681`, `:1706-1713`, `:2047-2052`
**Also:** `itrader/core/exceptions/portfolio.py:232-238`, `itrader/venues/venue_account_manager.py:19-26`, `:306-365`, `:400-443`, `:265-289`

**Issue:** `venue_manager` is a **local variable** inside `build_live_system`. Unlike
`facade._safety`, `facade._stream_recovery`, `facade._throttle`, `facade._feed_binder`,
`facade._config_router` and `facade._system_store`, it is never assigned onto the facade,
and `LiveTradingSystem` declares no `venue_accounts` attribute. A tree-wide grep confirms
the only uses of the manager are the three boot-loop calls
(`read_enabled_for` / `bring_online` / `rebind_feed`) plus the authority injection.

Consequences — every one of these is dead in production:

* `provision()` (ACCT-02 / D-26 / D-27, the phase's headline verb) has **zero production
  callers**. D-27's stated invariant — "An account provisioned at runtime must be usable
  in the SAME process, with no restart" — is not deliverable through any public API.
* `set_enabled()` and its D-33 `VenueAccountInUseError` refusal are unreachable, so the
  in-band half of the account-disable guard never runs. The docstring's "out-of-band case"
  is now the *only* case.
* `venue_uid_guard_active()` (D-15 / D-40, the per-pair security-guard status surface) has
  no reader — the D-04 guard's armed/inert outcome is not observable by any operator.
* `account_for()` (the COMP-07 seam) has no production caller.
* `VenueAccountNotProvisionedError` instructs the operator to run
  `system.venue_accounts.provision(venue, account_id, ...)` — an `AttributeError` on the
  real object. The one remediation string an operator will follow is wrong.

This is a false-green: `tests/unit/venues/test_venue_account_manager.py` and
`tests/integration/test_account_provisioning_loop.py` both construct
`VenueAccountManager(...)` directly, so all 34 provisioning tests pass while the object is
unreachable from a built system.

**Fix:** attach the manager beside the other collaborators and expose it under the name the
docstrings and the exception message already promise.

```python
# live_trading_system.py — beside `facade._feed_binder = feed_binder` (~:2052)
facade._venue_manager = venue_manager

# LiveTradingSystem, near the other read-through properties
@property
def venue_accounts(self) -> Any:
    """The venue-ACCOUNT domain owner (D-26). ``None`` on the in-memory arm."""
    if self._venue_manager is None:
        raise StateError(
            "LiveTradingSystem", "no-sql-spine",
            required_state="built with a SQL spine (venue_accounts requires the durable store)",
            operation="venue_accounts")
    return self._venue_manager
```

Add an integration assertion that a system built by `build_live_system` can reach
`system.venue_accounts.provision(...)` — the current tests cannot see this gap.

### CR-02: a feed re-borrow silently blinds the live feed and disarms the data arm's halt path

**File:** `itrader/venues/feed_binder.py:150-170`
**Also:** `itrader/trading_system/live_trading_system.py:2086-2090`, `:786-799`

**Issue:** `FeedConnectionBinder.rebind` builds a brand-new `LiveDataProvider` and calls
`self._feed.set_provider(provider)` / `set_bar_sink` / `set_global_queue`. Three things it
does **not** do:

1. **It never subscribes the new provider.** `OkxDataProvider` streams only for symbols
   passed to `subscribe(symbol)` (`okx_provider.py:265`), and the only subscribe loop in
   the tree is in `LiveTradingSystem.start()` (`:797-799`), which runs once at boot over
   `self.universe.members`. A re-borrow therefore installs a provider that will never
   emit a bar. The live engine goes bar-less with an INFO log that says
   `"Live feed RE-BORROWED its data connection"` — i.e. the log claims success.
2. **It never re-wires the safety seams.** `set_halt_signal` /
   `set_stream_state_listener` are applied exactly once, at boot, to the first-bound
   provider (`live_trading_system.py:2087-2090`). The code comment there even admits it:
   *"A runtime re-borrow re-wires its own halt signal off this same seam when that path
   lands"* — it has not landed. After a re-borrow the data arm has **no halt signal** (a
   connector-fatal on the candle stream cannot freeze the engine) and **no stream-state
   listener** (`_on_venue_stream_down` never fires, so submission is never paused when the
   candle stream drops).
3. **It never stops the old provider.** The previous provider is dropped on the floor with
   its `bar_sink` still pointing at `self._feed.update` and its consume task still running
   under its own `StreamSupervisor`. Two providers can then push into the one
   single-writer ring, and the abandoned credential-bearing object has no owner and no
   halt path — the exact WR-07 defect class `venues/assemble.py:8-18` says D-14 removed.

`tests/unit/venues/test_feed_binder.py:141` asserts only that the provider object changed
and that a switch was logged; it asserts nothing about subscription, safety wiring or
teardown, so this passes green.

**Fix:** make the binder own the whole re-borrow, not just the object swap.

```python
# feed_binder.py — inject the wiring/teardown seams at construction
def __init__(self, *, feed, data_registry, ctx, connectors, global_queue,
             wire_provider=None, symbols=None):
    ...
    self._wire_provider = wire_provider or (lambda p: None)   # halt + stream-state listeners
    self._symbols = symbols or (lambda: [])                    # live universe members

def rebind(self, available):
    ...
    provider = self._data_registry.get(spec.data_provider).build_provider(
        self._ctx, spec, self._connectors)
    provider.set_bar_sink(self._feed.update)
    provider.set_global_queue(self._global_queue)
    self._wire_provider(provider)                # halt signal + stream-state listener
    for symbol in self._symbols():               # a re-borrow must re-subscribe
        provider.subscribe(symbol)
    old, self._provider = self._provider, provider
    self._feed.set_provider(provider)
    if old is not None:
        try:
            old.stop()                            # never abandon a live credentialed stream
        except Exception:
            self.logger.error("previous feed provider teardown failed", exc_info=True)
```

If re-borrow cannot be made safe this phase, `rebind` must **refuse** a switch (raise /
halt) rather than perform a silently-degraded one.

### CR-03: reconnect-resume no longer takes any venue snapshot — the "never resume blind" contract is inert

**File:** `itrader/trading_system/live_trading_system.py:1788`, `:2027`
**Also:** `itrader/trading_system/safety/stream_recovery_handler.py:179-180`, `:142-202`

**Issue:** `venue_accounts: Dict[str, Any] = {}` is declared at `:1788` with the comment
"declared here so the facade construction, the StreamRecoveryHandler and the halt-signal
wiring below see them on EVERY path" — and is then **never written to**. The store-derived
boot loop (`:1834-1836`) populates only `venue_lifecycles`; the deleted
`_attach_venue_accounts` helper was the sole writer.

`StreamRecoveryHandler` is constructed with
`venue_accounts=lambda: list(venue_accounts.values())` (`:2027`), so
`for account in _distinct(self._venue_accounts()): account.snapshot()`
(`stream_recovery_handler.py:179-180`) iterates an empty list forever. `on_reconnect` then
falls straight through to `self._safety.resume_submission()`.

The handler's own docstring states the invariant this breaks:
*"Takes a fresh REST balance/position SNAPSHOT (don't trade when you can't see the venue)
… Never resume blind."* After this phase, submission resumes after every reconnect against
a venue cache that was last refreshed before the outage.

This is compounded by CR-01/COMP-07: since live portfolios now sit on compute leaves,
`Account.is_venue_truth` is `False` everywhere, so
`ReconciliationCoordinator.run_startup_reconcile` (`:171`, `:291`) and the baseline-residual
HALT are *also* skipped. The entire venue-truth safety layer is now silently inert in live,
with no log or status flag reporting it.

**Fix:** derive the account set from the live portfolio registry instead of a map nothing
writes, so it cannot go stale or empty by omission:

```python
# live_trading_system.py — replace the never-populated dict
stream_recovery = StreamRecoveryHandler(
    safety=safety,
    lifecycles=venue_lifecycles,
    venue_accounts=lambda: [
        p.account for p in portfolio_handler.all_portfolios().values()
        if getattr(p.account, "is_venue_truth", False)
    ],
    feed_provider=(lambda: feed_binder.feed_provider if feed_binder is not None else None),
)
```

Additionally, surface the COMP-07 deferral: log WARNING once at boot when a live system
comes up with zero venue-truth accounts, so "the venue reconcile / drift halt / resume
snapshot are all inert" is an observable state rather than an inferred one.

### CR-04: `bring_online` makes an account routable before anything connects or halt-wires it

**File:** `itrader/venues/venue_account_manager.py:505-531`
**Also:** `itrader/trading_system/live_trading_system.py:770-771`, `:818-822`, `:2091-2098`, `:955-957`

**Issue:** `bring_online` performs four steps and step (3) writes
`self._registry[(venue_name, account_id)] = bundle.exchange` — the **same map**
`ExecutionHandler.on_order` reads (`execution_handler.py:301`). From that instant the
account is order-routable. But `bring_online` does **not**:

* call `lifecycle.start()` (the connector `connect()` + the D-04 UID guard),
* call `bundle.exchange.connect()` (the sole spawn site for `_stream_fills` /
  `_stream_orders`),
* wire `bundle.exchange.set_halt_signal` / `set_stream_state_listener` /
  `bundle.connector.set_halt_signal`,
* register the lifecycle in `facade._venue_lifecycles`.

At boot this is masked, because `build_live_system` collects the lifecycles into
`venue_lifecycles` (`:1836`) and `LiveTradingSystem.start()` performs all four steps
afterwards. For a **runtime** `bring_online` — the entire point of D-27 — none of them
happen, and there is no code path anywhere that would. The result is an account whose
exchange accepts routed orders against an unconnected session, whose fill/order streams are
never spawned (its order mirror stays PENDING forever, the exact defect CR-01 of the earlier
phase fixed for the primary), whose connector-fatal never halts the engine, whose down
streams never gate `resume_submission`, and which `stop()` never tears down.

The `bring_online` docstring says only *"Returns the `OnlineVenueAccount` so a caller can
drive the lifecycle it built"* — but no runtime caller exists (CR-01), and when one is added
it will inherit an unsafe default ordering: **registered-then-connected** rather than
connected-then-registered.

**Fix:** register **last**, after the session is live and wired. Give the manager an injected
`on_account_online(record)` callback that the composition root supplies, doing exactly what
`start()` does per lifecycle:

```python
# venue_account_manager.py::bring_online — reorder so a half-built account is unroutable
bundle, lifecycle = assemble_venue(...)
record = OnlineVenueAccount(spec=spec, bundle=bundle, lifecycle=lifecycle)
# (a) connect + arm the D-04 guard, (b) wire halt/stream-state, (c) spawn the venue streams.
#     Injected by the composition root; at boot it is the same body start() runs.
self._on_account_online(record)
# (d) ONLY NOW is the pair routable.
self._registry[(venue_name, account_id)] = bundle.exchange
self._online[(venue_name, account_id)] = record
self.rebind_feed()
return record
```

Add a test that asserts `_registry` does **not** contain the pair when the connect step
raises — today a failed connect leaves a routable, unconnected exchange behind.

### WR-01: `provision()` accepts config keys/values that make every later boot fail

**File:** `itrader/venues/venue_account_manager.py:306-365` (write) vs `:574-668` (validation)
**Also:** `itrader/trading_system/live_trading_system.py:1834-1836`

**Issue:** `provision()` persists `config` verbatim (only the store's secret-key denylist
runs). The allowlist check (`_merge_account_config`) and the value checks
(`_assert_config_values`) run **only** in `bring_online`. So `provision(venue, acct,
config={"sandox": True})` writes an `enabled=True` row happily, and the *next* boot's
unguarded loop `for row in venue_manager.read_enabled_for(exchange):
venue_manager.bring_online(row)` raises `UnknownVenueAccountConfigKeyError` straight out of
`build_live_system`. The engine cannot start at all, and the only remedy is a manual SQL
edit — there is no in-band way to correct or disable the row, because `set_enabled` is
unreachable (CR-01).

**Fix:** validate at the write boundary too (the check is pure and already extracted), and
decide the boot policy explicitly:

```python
def provision(self, venue_name, account_id, *, secret_ref=None, config=None):
    normalized = dict(config) if config is not None else {}
    # Same allowlist + value rules bring_online applies — refuse at WRITE time so a typo
    # can never persist an enabled row that bricks the next boot (D-38).
    self._merge_account_config(venue_name, account_id, normalized)
    self._create_row(...)
```

and either wrap the boot loop per-row (skip + CRITICAL alert, matching
`rehydrate_strategies`' per-instance quarantine) or document that one bad row is a
deliberate refuse-to-start.

```python
if self._store.get(venue_name, account_id) is None:
```

### WR-03: `add_portfolio` writes the durable row before ACCT-03 and the portfolio cap are checked

**File:** `itrader/portfolio_handler/portfolio_handler.py:283-302`, `:405-416`
**Also:** `itrader/portfolio_handler/rehydrate/portfolio_rehydrate.py:151-159`, `itrader/trading_system/live_trading_system.py:1849-1853`

**Issue:** `add_portfolio` runs `self.create(...)` (the durable `portfolios` INSERT) **and
then** `self.materialize(...)`, which is where the ACCT-03 gate
(`VenueValidatedComputeAuthority` → `assert_available`) and the `max_portfolios` cap live.
The docstring justifies the ordering with *"a create that succeeds followed by a materialize
that raises leaves a durable row with no live Portfolio — the next boot rehydrates it, so the
row is not orphaned"*. That reasoning is inverted for two reachable in-band cases:

* the account row exists but is **disabled** — the composite FK is satisfied, so `create`
  succeeds; `materialize` then raises `VenueAccountNotProvisionedError(DISABLED)`. The next
  boot's `rehydrate_portfolios` (`portfolio_rehydrate.py:151`) calls `materialize` with no
  try/except and the exception propagates out of `build_live_system` — the engine cannot
  start;
* the portfolio count is already at `max_portfolios` — same shape: durable row written,
  registration refused, next boot fails partway through with a partial set registered
  (already FLAGGED in the rehydrate docstring, but the create-first ordering is what makes
  it reachable without any out-of-band writer).

**Fix:** validate before persisting. Either resolve the account leaf first and write the
definition row only on success, or run the two guards up front:

```python
# add_portfolio — cheap pre-checks before the durable write
if portfolio_id is not None and self.has_portfolio(resolved_id):
    raise PortfolioValidationError(resolved_id, "portfolio_id", "already registered")
if len(self._portfolios) >= self.max_portfolios:
    raise PortfolioConfigurationError("max_portfolios", self.max_portfolios,
                                      "maximum portfolios limit reached")
portfolio = self.materialize(...)   # ACCT-03 raises here, before anything is persisted
self.create(portfolio.portfolio_id, name=name, cash=cash,
            account_id=account_id, venue_name=venue_name)
```

Independently, `rehydrate_portfolios` should quarantine a single unmaterializable row
(skip + CRITICAL alert) rather than aborting the whole boot.

### WR-04: security-guarantee docstrings overstate what the ACCT-03 check does

**File:** `itrader/portfolio_handler/portfolio_factory.py:123-146`, `:216-232`
**Also:** `itrader/trading_system/live_trading_system.py:1659-1663`

**Issue:** `assert_available` deliberately checks **EXISTS + ENABLED only**, and documents
at length why "brought online" is intentionally *not* checked
(`venue_account_manager.py:683-694`). Three separate places claim otherwise:

* `VenueValidatedComputeAuthority` docstring: *"asks the `VenueAccountManager` to assert
  the pair is provisioned + enabled + brought-online"* (`portfolio_factory.py:127-129`);
* `PortfolioFactory.materialize` docstring: *"the live authority RAISES ACCT-03 on a
  missing/disabled/not-online account and yields a venue-truth leaf otherwise"*
  (`portfolio_factory.py:252-255`) — it yields a **compute** leaf;
* `build_live_system` comment: *"VALIDATE the pair (exists + enabled + brought-online)"*
  (`live_trading_system.py:1660-1661`).

These are load-bearing claims about the phase's stated security guarantee, in a codebase
whose convention is decision-anchored docstrings. A maintainer reading them will believe a
not-online account cannot back a live portfolio; it can.

**Fix:** correct all three to "provisioned + enabled (the brought-online check lives on
`account_for`, the COMP-07 seam)" and drop "yields a venue-truth leaf" in favour of the
accurate "builds a COMPUTE leaf carrying the real pair (COMP-07 / Phase 12)".

### WR-05: the create_all-vs-migration parity gate does not cover indexes — the phase's only schema change is unguarded

**File:** `tests/integration/storage/test_migrations.py:255-338`
**Also:** `migrations/versions/p112_portfolios_is_deleted.py:29-35`, `itrader/storage/portfolio_definition_store.py:150-166`

**Issue:** `test_create_all_vs_migration_parity` compares **table name sets** and
**per-table column-name sets** only. It never calls `inspector.get_indexes(...)` or
`get_unique_constraints(...)`. The whole of 11.2's schema work is an index/constraint swap:
drop `uq_portfolios_venue_name`, create the partial `uq_portfolios_live_account … WHERE NOT
is_deleted`. A migration that created a **plain** unique index, omitted `sqlite_where`, or
left the old constraint in place would pass parity unchanged.

Both the migration and the registrar docstrings assert the opposite — *"a divergence here
silently splits the test-path and prod schemas, which is exactly what the
create_all-vs-migration parity gate exists to catch"*. The registrar side is well covered
(`test_portfolio_definition_store.py:664-706` asserts the declared shape and the spike
proves the SQLite predicate bites), but **no test inspects the migrated engine's index**.

I verified by hand that the chain is currently correct: `upgrade head` on SQLite yields
`CREATE UNIQUE INDEX uq_portfolios_live_account ON portfolios (venue_name, account_id) WHERE
is_deleted = 0` with `get_unique_constraints('portfolios') == []`, byte-identical to
`create_all`. The gate simply cannot see it.

**Fix:** extend the parity assertion:

```python
def _index_shape(inspector, table):
    return {
        (idx["name"], tuple(idx["column_names"]), bool(idx["unique"]),

    }

for table in _NEW_TABLES:

            == inspector_b.get_unique_constraints(table))
```

### WR-06: `VenueLifecycle.stop()` tears down every account's connector, not its own

**File:** `itrader/venues/lifecycle.py:202-214`
**Also:** `itrader/trading_system/live_trading_system.py:920`, `:955-957`

**Issue:** `stop()` prefers `self._connectors.close_all()`, and `ConnectorProvider.close_all`
disconnects **every** memoized connector for the run and clears the memo
(`connectors/provider.py:154-166`). Since 11.2 there is one `VenueLifecycle` **per account**
and each holds the same shared `ConnectorProvider`, so stopping account A's lifecycle
disconnects accounts B..N as well. The facade's teardown loop then calls `stop()` once per
lifecycle (`:955-957`), and every call after the first operates on an already-cleared memo.

Today this is masked because teardown is all-or-nothing at `stop()`. It becomes a live
defect the moment a single account is retired at runtime (D-27's premise) — retiring one
account kills every other account's session.

**Fix:** make `stop()` scoped to its own bundle, and keep `close_all()` as an explicit
run-level teardown owned by the composition root:

```python
def stop(self) -> None:
    """Disconnect THIS account's connector only (the shared memo is run-scoped)."""
    if self._bundle.connector is not None:
        self._bundle.connector.disconnect()

# live_trading_system.stop() — after the per-lifecycle loop
if connectors is not None:
    connectors.close_all()
```

### WR-07: `PortfolioHandler.definition_store` is gated on `environment == "live"`, silently disabling all portfolio durability

**File:** `itrader/portfolio_handler/portfolio_handler.py:120-125`
**Also:** `itrader/trading_system/live_trading_system.py:1809-1815`

**Issue:** the definition store is built only when `environment == "live" and sql_engine is
not None`. `compose_engine`'s `route_orders_by_account` is deliberately decoupled from
`ctx.environment` ("so a live system built with a test environment string still routes by
account"), but durability is not. A live system built with `environment="test"` and a real
SQL spine gets `definition_store = None`, so `create()` no-ops, `deactivate/activate/delete`
persist nothing, `assert_distinct_accounts` is skipped and `rehydrate_portfolios` never runs.

Worse, the "first start" warning is itself gated on `definition_store is not None`
(`live_trading_system.py:1811`), so this configuration boots with **zero portfolios and zero
log output** — precisely the "silent zero-portfolio boot" D-19 forbids and the surrounding
comments claim to prevent.

**Fix:** gate on the presence of the spine, or log loudly when a SQL-backed live boot has no
definition store:

```python
if sql_engine is not None and environment == "live":
    ...
elif sql_engine is not None:
    self.logger.warning(
        "A SQL spine is wired but environment=%r — portfolio DEFINITIONS will NOT be "
        "persisted and nothing will rehydrate on restart.", environment)
```
