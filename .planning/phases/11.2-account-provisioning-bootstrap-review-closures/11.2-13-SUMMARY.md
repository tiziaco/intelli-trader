# Phase 11.2 Plan 13: on_order fail-closed REFUSED emission + phantom-invariant docstring gate Summary

`ExecutionHandler.on_order`'s two surviving fail-closed paths (unknown portfolio; unregistered
`(venue, account_id)` pair) now emit a distinctly-coded `FillEvent(REFUSED)` instead of a silent
`logger.error` + `return`, so a misconfigured live engine's dropped orders are observable in the event
stream and reconcile the order mirror out of `PENDING`; the unreachable `account_id is None` middle
branch is deleted; and all three phantom-invariant docstrings (that mis-attributed account-id
mandatoriness to plan 11-08) are corrected and pinned by a new static gate.

## Deviations from Plan

**1. [Rule 2 - Missing critical functionality] Added `error_code` to `FillEvent` (fill.py not in `files_modified`)**
- **Found during:** Task 2, while wiring the REFUSED emission.
- **Issue:** `ExecutionErrorCode` lives only on `ExecutionResult` (a return channel); `FillEvent` had no `error_code` field and `on_order` has no return channel — it emits directly to the queue. The plan's backstop must_have ("distinguishable by error code alone, **without reading the log**") plus the D-42 truth and Task-2 acceptance ("the REFUSED fill **carries** the code", "assert on the emitted event and its error code, not log text") are only satisfiable if the code is on the event.
- **Fix:** Added `error_code: ExecutionErrorCode | None = None` to `FillEvent` and a keyword-only `error_code` param to `FillEvent.new_fill`. Default `None` → EXECUTED and the simulated exchange's own REFUSED fills carry none (oracle-dark; backtest byte-exact preserved). `simulated._emit_rejection` was left unchanged.
- **Files modified:** `itrader/events_handler/events/fill.py`
- **Commit:** `043b9986`
- **Note for wave-merge:** if a sibling wave-7 plan also edits `fill.py`, this additive field may need a trivial merge.

**2. [Rule 3 - Blocking (typing)] Type-narrowing lookup guard after deleting the middle branch**
- **Issue:** deleting `if account_id is None: return` left `account_id: str | None` flowing into `self.exchanges.get((event.exchange, account_id))`, which mypy `--strict` rejects (registry keyed `tuple[str, str]`).
- **Fix:** `exchange = self.exchanges.get((event.exchange, account_id)) if account_id is not None else None`. A None account resolves to no exchange → the same pair-miss refusal the deleted branch produced. Grep-safe (`is not None`, not the prohibited `if account_id is None`), no `DEFAULT_ACCOUNT_ID` coercion.
- **Commit:** `043b9986`

**3. [Acceptance-criterion correction] `grep -c 'or DEFAULT_ACCOUNT_ID' == 0` is false-failing**
- The pre-change tree already returns **1**: the load-bearing MPORT-07 warning inside the read-model docstring (`It must NEVER be written as account_for(...) or DEFAULT_ACCOUNT_ID`), which the plan explicitly says to KEEP. The `== 0` criterion can never pass while that warning exists.
- **Discriminating replacement (applied):** the only occurrence remains the docstring warning (line 174) — no executable coercion was added. Post-change count is 1, warning-only. Verdict: intent (no coercion added) satisfied.

**4. [Self-corrected during execution] Initial Task-2 middle-branch comment reproduced the phantom**
- My first draft of the deleted-branch comment said "the composition-time raise (plan 11-08) makes it unreachable" — the exact phantom ACCT-06 removes. Before finalizing Task 2's edits I rewrote it to attribute the guard to the ACCT-03 materialize-time `VenueAccountManager.assert_available` raise. No phantom shipped.
