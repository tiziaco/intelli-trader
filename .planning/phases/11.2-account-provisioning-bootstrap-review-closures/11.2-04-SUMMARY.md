# Phase 11.2 Plan 04: Reject the enable_margin runtime flip Summary

**Two-layer, key-scoped typed refusal of the `enable_margin` runtime flip — a denylist consulted by both `ConfigRouter._apply_portfolio` and `Portfolio.update_config`, surfaced as `ImmutableConfigKeyError` and caught by `apply()` as a deduped `immutable-key` rejection.**

## Performance

- **Duration:** ~25 min
- **Started:** 2026-07-23T15:44:00Z
- **Completed:** 2026-07-23T16:08:49Z
- **Tasks:** 3
- **Files modified:** 7

## Accomplishments

- `enable_margin` is no longer routable at runtime. It was a `TradingRules` field inside a mutable section, so the router merged, validated and swapped it into the live config while notifying nobody — silently desynchronizing four of its five readers (`AdmissionManager._enable_margin`, `EnhancedOrderValidator.enable_margin`, `ManagedStrategies.enable_margin`/SHORT-01 and the account leaf's very KIND all bind at construction; only `Portfolio.process_transaction` re-reads per fill).
- The refusal is a **single set consumed twice**: `IMMUTABLE_PORTFOLIO_CONFIG_KEYS` lives in `itrader/config/portfolio.py` beside the field it governs, and both the router gate and the domain backstop read it, so the two layers cannot disagree about what is immutable.
- `ImmutableConfigKeyError` carries structured `key`/`scope` and builds a message naming the **consequence** (which four readers desynchronize) and the **remediation** (recreate the portfolio with the desired margin setting).
- The typed refusal is explicitly caught in `ConfigRouter.apply()` and surfaced as the standard deduped WARNING rejection with a new `immutable-key` reason — closing a silent-failure path the plan never addressed (see Deviations #4).
- The backstop **walks the payload at every depth**, because `recursive_merge` accepts nested blobs and a top-level-only check is bypassable by nesting the key inside its section.
- The tightening is key-scoped: `_PORTFOLIO_MUTABLE_SECTIONS` is unchanged and `limits`, `risk_management` and every sibling `trading_rules` field stay routable — pinned by three tests, including a structural assertion on the section tuple.

## Decisions Made

1. **The denylist lives in `itrader/config/portfolio.py`, not `config_router.py`.** The plan asked for a module-level frozenset in the router, but the plan's own Task 2 requires that "the two must not be able to drift apart" — only a shared constant guarantees that. `portfolio_handler` importing from `trading_system` would invert the layering, so the model module (which already defines `enable_margin` and is already imported by both) is the only correct shared home. Placing it adjacent to the field also means a future construction-bound field is added under the reader's nose.
2. **`ImmutableConfigKeyError` is caught, not left to escape.** See Deviations #4 — this is the load-bearing correctness call in this plan.
3. **`_resolve_portfolio_section` was left untouched.** It is a `@staticmethod` documented to return `None` for default-deny; raising from it would break that contract. The guard sits strictly earlier, at the top of `_apply_portfolio`.
4. **The guard fires before portfolio-id resolution.** Immutability is a property of the key, not of the addressed portfolio, so an unknown id carrying `enable_margin` rejects with `immutable-key` rather than `unknown-portfolio`, and no store is read at all.
5. **`PortfolioHandler.update_config` is deliberately NOT guarded.** It mutates `config_data`, the TEMPLATE config used when constructing new portfolios (verified at `portfolio_handler.py:1596-1615`; it does not touch live portfolios). Setting `enable_margin` there is a construction-time setting, which is exactly the remediation the exception recommends — guarding it would break the only supported path to a margin portfolio. `test_max_leverage_update_preserves_sibling_trading_rules` continues to exercise that path.

### 2. [Audit item 2 — false-green acceptance criterion] Replaced two grep gates

- **Found during:** Task 1 (pre-change criterion run, per the audit warning)

  The section-tuple criterion (`grep -c '_PORTFOLIO_MUTABLE_SECTIONS = ("limits", "risk_management", "trading_rules")'` → 1) was valid and still returns `1`; it is additionally pinned as a test assertion so a future removal fails the suite, not just a grep.

### 4. [Audit item 6 / Rule 2 — missing critical] The typed refusal would have escaped `ConfigRouter.apply()`

- **Found during:** Task 1
- **Issue:** `apply()` surfaces refusals only via `_RejectedUpdate`, with a second arm catching `(SQLAlchemyError, ConfigurationError, pydantic.ValidationError)`. `ImmutableConfigKeyError` follows the plan's own `DuplicateVenueAccountError` template, whose base chain is `PortfolioError(ITraderError)` — matched by neither arm. Left as-is, a refused operator knob would have escaped to the engine error boundary and become an ErrorEvent/handler-error path in live mode instead of the deduped WARNING every other default-deny produces. The plan never addressed this, and unit tests calling `_apply_portfolio`/`update_config` directly would have gone green either way.
- **Fix:** Added `_REASON_IMMUTABLE_KEY = "immutable-key"` (a distinct category from `unknown-key`, which means "no such field") and an explicit `except ImmutableConfigKeyError` arm in `apply()` that routes through `_surface_rejection`. The typed exception is preserved for direct callers of `Portfolio.update_config`; the queue-facing boundary keeps its own protocol.
- **Verification:** `test_immutable_enable_margin_refusal_does_not_escape_apply` calls `router.apply(...)` directly and asserts no raise plus the `immutable-key` warning.
- **Committed in:** `a7436ad7`

### 5. [Rule 3 — blocking] Worktree editable-install shadowing produced a false RED-after-GREEN

- **Found during:** Task 1 GREEN
- **Issue:** `poetry run pytest` in this worktree imports `itrader` from the **main checkout** via the editable install (the worktree has no `.venv`), so the new guard was invisible to the suite and the GREEN run still failed. `poetry run python -c` masked it (cwd is on `sys.path[0]`), as did `mypy` (`files = ["itrader"]` is path-relative).
- **Fix:** Every verification run in this plan was executed with `PYTHONPATH=<worktree root>` (and `MYPYPATH` for mypy). Confirmed the shadowing directly (`import itrader.config.portfolio` resolved through the main tree under pytest).
- **Note for the merge/verify step:** re-run the gate from the main checkout after merge; results here are only valid with `PYTHONPATH` set.

### 6. [Plan drift — stale count] mypy reports 260 source files, not 282

- **Issue:** All three tasks' acceptance criteria say "mypy reports success over 282 source files". The tree has exactly **260** `.py` files under `itrader/`, and mypy reports 260 both before and after this plan.
- **Fix:** Treated "mypy clean" as the criterion. No file was added or removed by this plan, so the count is unchanged from baseline.
