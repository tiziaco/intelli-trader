## Spike result — the evidence the checkpoint asked for

RESEARCH Assumption A6 (MED, zero in-tree precedent) is now **evidence: the mechanism works.**

`Index("...", table.c.venue_name, table.c.account_id, unique=True, postgresql_where=~table.c.is_deleted, sqlite_where=~table.c.is_deleted)`
emits a genuine partial predicate on **both** dialects:

```
SQLITE  : CREATE UNIQUE INDEX uq_spike_live ON spike_portfolios (venue_name, account_id) WHERE is_deleted = 0
POSTGRES: CREATE UNIQUE INDEX uq_spike_live ON spike_portfolios (venue_name, account_id) WHERE NOT is_deleted
```

SQLite renders `is_deleted = 0` because its Boolean is an INTEGER affinity; the predicate is
semantically identical to Postgres' `NOT is_deleted`. The predicate is a SQLAlchemy column
expression (`~column`), not a raw string, so one object serves both dialect kwargs and the
dialects cannot drift.

Three assertions pass on SQLite (`12 passed`), and they are mutually non-vacuous — a silently
ignored `sqlite_where` would degrade the index to PLAIN and fail (a); a dropped index would
fail (b) and (c):

- (a) a RETIRED row and a LIVE row on the same `(venue_name, account_id)` both persist — sequential reuse works
- (b) two LIVE rows on one pair raise `IntegrityError` — simultaneous sharing still DB-refused (T-11.2-02-01)
- (c) flipping a retired row back live while a successor holds the pair raises `IntegrityError` — self-enforcing in both directions
