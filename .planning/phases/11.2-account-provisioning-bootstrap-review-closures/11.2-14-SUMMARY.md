# Phase 11.2 Plan 14: D-29 fresh-deployment provisioning gate + phase close Summary

The phase finale, RE-SCOPED by owner decision (wave 8, 2026-07-24). D-29's fresh-deployment
provisioning gate now walks the entire zero-account-to-live-portfolio-to-refused-duplicate loop in
one integration test on an in-memory SQLite spine, constructing the `VenueAccountManager` directly
(a VAM is not reachable via the facade, D-35). The two composition tests and `scripts/run_live_paper.py`
were correctly left untouched. Every phase gate is green with measured values recorded below.

## What was built

**Task 1 — D-29's six-step gate (`test_fresh_deployment_provisioning_gate_walks_the_whole_loop`).**
Extended plan 05's 3-test tracer into a fourth test that performs the full fresh-deployment sequence
on ONE spine and ONE `VenueAccountManager` instance, with no restart between steps:

1. A zero-account boot comes up empty: `read_enabled_for` returns `[]` and the exchange registry is
   empty, no exception (ACCT-01/D-09).
2. `add_portfolio` BEFORE provisioning refuses with the typed `VenueAccountNotProvisionedError`
   (cause `NOT_PROVISIONED`), never a bare `KeyError`/`AttributeError` and never a silent compute
   leaf (ACCT-03).
3. `provision(venue, account_id, secret_ref=...)` — the create-only verb, not a raw store write —
   writes exactly one `venue_accounts` row; the account id is stored verbatim and reads back
   byte-for-byte (ACCT-03 exact-string encoding).
4. `bring_online(row)` registers the exchange under the exact `(venue, account_id)` pair and NOT
   under the coerced `(venue, 'default')` — usable in the same process, same manager instance (D-27).
5. The next `add_portfolio` SUCCEEDS on a COMPUTE `SimulatedCashAccount` leaf carrying the real
   `(venue, account_id)` pair (`portfolio.account_id == account_id`, `portfolio.venue_name == venue`,
   `balance == Decimal("10000.00")`) — `is_venue_truth` is NOT asserted (COMP-07/Phase 12, D-23).
6. A second `provision` of the same pair refuses with the typed
   `DuplicateVenueAccountProvisionError` and leaves the row count at exactly 1 (ACCT-02/D-11).

The "add_portfolio" seam is the live portfolio-creation path verbatim: a `PortfolioFactory` over a
`VenueValidatedComputeAuthority` wrapping the REAL `VenueAccountManager` (the arm the live composition
root injects), assembled on the spine. The fixture was extended to expose the shared `VenueBundles`
memo so the portfolio authority and the manager share ONE memo (D-08), matching the real composition.

**Task 2 — no change needed.** The plan's "add a `provision(...)` line to `scripts/run_live_paper.py`
and finish D-37's residue" was RE-SCOPED away. `scripts/run_live_paper.py` is untouched (its
`--mode replay` CI path uses the compute authority, has no SQL spine, and is oracle byte-exact; the
facade has no `venue_accounts` handle and D-35 forbids adding one). Both composition tests were already
rewritten against public seams by merged waves 07/09/11; verified green (20 passed), no port, no delete.
